# actflow — спецификация

[English](SPEC.md)

Библиотека исполнения графов задач. Связи описывают, куда идут результаты, задачи — что вычисляет один такт, контроллеры решают, когда что случается, а исполнитель прогоняет значения по графу по мере их появления. Этот документ описывает actflow 0.2.0.

## 1. Базовая идея

```
Топология решает, куда.
Контроллеры решают, когда.
Задачи решают, что.
Исполнитель применяет изменения состояния.
```

Задача только считает: она получает значения и испускает результаты, не зная, кто их потребляет, — маршрутизация принадлежит связям. Тело — чистая функция одного такта и не хранит состояния между запусками; всё, что тянется во времени (готовность, порядок, батчи, доставка), живёт в контроллерах. Состояние прогона меняет только исполнитель: он однопоточен, и управление переключается лишь в точках await, никогда вытеснением.

## 2. Задачи и тела

Наследуйте `Task` и определите `execute` с именованными параметрами. Имена параметров — это входы узла, выведенные из сигнатуры при создании класса; у variadic-тела (`*args` / `**kwargs`) фиксированной арности нет, и оно падает при построении узла.

Любой контроллер исполнения принимает четыре формы тела (интерфейс приводит их к одному потоку до исполнения):

```python
class Plain(Task):
    def execute(self, value):
        return Downstream(value + 1)


class Coro(Task):
    async def execute(self, value):
        return GraphOutput(await lookup(value))


class Gen(Task):
    def execute(self, value):
        for part in value:
            yield Downstream(part)


class AsyncGen(Task):
    async def execute(self, value):
        async for part in stream(value):
            yield GraphOutput(part)
```

Тело испускает объекты-результаты:

- `Downstream(value, output="next", shared=True)` идёт дальше по графу через названный выход.
- `GraphOutput(value)` покидает граф и отдаётся вызывающему `Executor.run`.
- Возврат `None` — или генератор, не выдавший ничего, — не испускает ничего.

Всё остальное поднимает `TypeError` при диспетчеризации. Разделяемый (`shared`) `Downstream` вручает каждому получателю одну и ту же ссылку; копирование — дело задачи.

С библиотекой идут две крошечные задачи: `Input` пересылает своё значение на `next`, `Tap` выполняет побочное действие и пересылает дальше.

## 3. Топология

Экземпляр `Task` — это конфигурация; вызов строит узел, и каждый вызов строит новый, со своими копиями контроллеров:

```python
node = MyTask()()
```

Соединяйте через `>>`. `node["name"]` — порт; вход это или выход, решает его сторона оператора:

```python
a >> b
a >> b["inp"]
a["out"] >> b
a["out"] >> b["inp"]
```

`a >> b` соединяет каждый выход `a` с каждым входом `b`; именованный порт сужает свою сторону до одного имени. `>>` возвращает целевой узел, поэтому цепочки читаются слева направо: `a >> b >> c`.

Проверка асимметрична. Входы известны из сигнатуры `execute`, поэтому `a >> b["typo"]` падает при соединении. Выходы нигде не объявляются: узел может испустить любое имя в любой момент, левую сторону проверить нельзя, а значение на выходе, который никто не подключил, молча отбрасывается. Цели — множества, поэтому дубли рёбер схлопываются: и повторное соединение той же пары, и безымянное ребро рядом с именованным в тот же вход доставляют один раз.

Граф может расти во время прогона: `wire` берёт блокировку узла и может вызываться из любого потока, а адресация ленива — новое ребро действует со следующего испущенного значения. `node.coverage()` возвращает узел и всё достижимое из него по рёбрам. `node.clear()` сбрасывает это покрытие в начальное состояние контроллеров (проводка цела); `node.clone()` строит независимого двойника — те же задачи и проводка, свежее состояние; ресурсы прототипов вроде пула нитей остаются общими.

## 4. Контроллеры — прототипы

У узла три контроллера и политика маршрутизации:

- контроллер ввода — держит пришедшие значения и решает, когда телу можно запускаться
- контроллер вывода — владеет доставкой: куда идёт произведённое значение, как и когда
- контроллер исполнения — запускает тело и решает, где оно выполняется
- политика маршрутизации — выбирает единственного получателя неразделяемого значения

Все четыре наследуют `Controller`, а их подклассы автоматически становятся dataclass-ами с полями только по имени, так что аннотированный атрибут — это настройка. Экземпляр, переданный в `Task(...)`, — прототип: каждый узел, построенный из задачи, берёт собственную рабочую копию через `replace`. Держите настройки в полях dataclass, а состояние узла — в `cached_property`, и копия будет стартовать чистой.

```python
Task(
    input_controller=None,
    output_controller=None,
    execution_controller=None,
    isolated=False,
    policy=None,
)
```

## 5. Сторона входа: вердикты

Контроллер ввода реализует `offer(delivery)`, `poll()` и `collect()` поверх стандартного словаря `queues` (список на каждый вход) и `queue(name)`. `offer` получает `Delivery` (значение — `delivery.value`, адресованный вход — `delivery.target.name`) и отвечает вердиктом; `poll` отвечает заново без новых данных:

- `Ready()` — запускай сейчас.
- `Wait()` — будить только по приходу новых данных.
- `WaitUntil(deadline)` — разбудить не позже дедлайна (секунды монотонных часов).

Контроллер никогда не спит и не владеет таймером: он называет дедлайн, а исполнитель паркует узел и будит его. Батч по времени не стоит ни потока, ни активного ожидания.

`collect()` забирает из очередей входы одного такта и возвращает `Collected(data, metadata)`: `data` передаётся как `execute(**data)`, `metadata` едет к контроллеру вывода того же такта. Исполнитель собирает атомарно вместе с вердиктом `Ready`, поэтому значение из очереди никогда не выдаётся дважды.

По умолчанию: `InputController` — FIFO, готов, когда непуста каждая входная очередь. `OrderedInputController` подаёт узлу с единственным входом значения в порядке `value["idx"]`, непрерывно от 0 — пропущенный индекс задерживает всё после себя — и штампует `metadata={"idx": n}`.

## 6. Сторона вывода и маршрутизация

Контроллер вывода вызывается один раз на каждое произведённое значение: `dispatch(result, metadata)` возвращает доставки, которые применит исполнитель, а пустой список значит, что значение придержано. Метод асинхронный, поэтому контроллер может дождаться своей очереди, прежде чем выпустить значение. `close_tick(metadata)` выполняется один раз, когда тело такта исчерпано.

Стандартный `OutputController` выпускает всё сразу. Разделяемый `Downstream` идёт каждому получателю, подключённому к этому выходу; `Downstream(..., shared=False)` — ровно одному, которого выбирает политика испускающего узла. Политика по умолчанию `ShortestQueue` берёт цель с самой короткой входной очередью; своя политика наследует `RoutingPolicyInterface` и реализует `choose(targets, value)`. Очереди копятся только у занятых получателей (isolated или медленный узел): у быстрых в момент выбора все очереди нулевые, и один получатель стабильно забирает всё.

`OrderedOutputController` возвращает порядок входа узлу, чьи такты идут параллельно: каждый `dispatch` ждёт, пока `metadata["idx"]` совпадёт с текущим ходом, а `close_tick` передвигает ход, так что такт, ничего не испустивший, всё равно передаёт его дальше. Ставьте его в пару с `OrderedInputController`, который штампует idx. Ожидающий `dispatch` держит слот исполнителя: значения idx, проштампованные не в порядке выдачи, могут застопорить прогон.

## 7. Контроллеры исполнения

`LocalExecutionController` (по умолчанию) отдаёт поток тела циклу событий как есть. Свой контроллер наследует `ExecutionControllerInterface` и реализует один метод `drive(stream)` — где исполняется нормализованный поток; четыре формы тела разбирает интерфейс до него.

`FiberExecutionController(threads=1, timeout=None, gateway=None, max_inflight=0)` запускает тело как нить (fiber): шаги выполняются в пуле из `threads` рабочих потоков, а каждый await возвращает управление центральному циклу. Тело может await-ить только то, что предлагает `self`:

- `self.sleep(delay)` — таймер; не держит рабочий поток.
- `self.loop_io(factory)` — выполнить async-фабрику на центральном цикле (например, aiohttp).
- `self.offload(fn)` — выполнить блокирующий вызов в пуле шагов, конкурируя за те же рабочие слоты.
- `self.remote(service, operation, payload)` — отправить в шлюз и дождаться ответа.

Голый `await` на чём-либо ещё падает во время выполнения, а не на построении. `timeout` — дедлайн на весь такт с момента получения inflight-слота: время в очереди за слотом не считается, время между результатами — считается. Он применяется в собственных точках ожидания контроллера: шаг в потоке прервать нельзя, поэтому просрочка всплывает по окончании идущего шага. Просрочка, целиком попавшая в последний шаг тела, не наказывается: работа уже сделана, результаты остаются в силе. Отмена бросается внутрь тела, поэтому синхронный `finally` выполняется; `finally` с `await` внутри дальше не продвигается. Поднятый затем `TimeoutError` завершает прогон, как любая ошибка тела. `max_inflight > 0` ограничивает число одновременных нитей контроллера — на каждый цикл событий свой счёт.

Все копии узлов одного прототипа делят один пул и один лимит `max_inflight`; передайте `pool=`, чтобы делить пул шире. Пул закрывает его создатель, а осиротевший пул присоединяется при выходе интерпретатора.

`RemoteGateway` — транспорт за `self.remote`: наследуйте его, реализуйте `async submit(service, operation, payload)` и передайте как `FiberExecutionController(gateway=...)`.

## 8. Исполнитель

```python
ex = Executor(max_parallel=8)
async for out in ex.run(start_node, seed):
    ...
```

`run` — асинхронный генератор: он подаёт начальное значение в стартовый узел, которому нужен ровно один вход, а затем отдаёт каждое значение `GraphOutput` по мере выхода из графа. Чтобы остановиться на первом результате, выходите из цикла под `contextlib.aclosing`.

Цикл ждёт следующего испущенного значения каждого работающего узла, а не завершения узла, поэтому первое значение тела-генератора уходит вниз по графу, пока тело ещё работает. Ожидание несёт таймаут от ближайшего дедлайна `WaitUntil`, и узлы с наступившим сроком опрашиваются заново. `max_parallel` — семафор, удерживаемый на весь такт. Состояние прогона держит только `Scheduler`, базовый класс исполнителя: кому можно запускаться сейчас, кто запаркован и до когда. Один Executor ведёт один прогон за раз; второй одновременный `run` поднимает ошибку. Состояние контроллеров живёт на узлах и переживает прогоны — прогон с нуля делается через `node.clear()`, независимая копия — через `node.clone()` и `ex.clone()`. Зовите `clear()` только между прогонами: сброс покрытия, которое исполнитель сейчас гонит, ломает этот прогон.

`isolated=True` на задаче значит, что два такта этого узла никогда не идут одновременно: пока такт работает, новые выдачи подавляются, а накопленные в очереди значения выдаются по его завершении.

Ошибка в теле завершает прогон: незавершённые такты отменяются, и исключение поднимается к вызывающему `run`.

## 9. Ломающие изменения относительно 0.1.x

- Ярлыки источника удалены: `label`, `in_labels` / `out_labels`, `input_map` / `output_map`, `slot_map`, `on_dropped`. Там, где несколько рёбер сходились в коллектор автопривязкой по ярлыку, соединяйте явно: `a >> collector["a"]`.
- Протокол результата сменился: возвраты-словари (`{"next": v}`, `{None: v}`), `TaskResult` и `self.to()` удалены. Испускайте `Downstream` / `GraphOutput` или yield-ите их из тела-генератора. Задача `Terminal` ушла вместе с `TaskResult`; возвращайте `GraphOutput`.
- Вместе с ним сдвинулся интерфейс контроллеров: `offer` получает `Delivery`, а `Packet` удалён, `Collected.mark` теперь называется `metadata`, а сторона вывода — асинхронный `dispatch(result, metadata)` на каждое значение плюс `close_tick` вместо `emit(results, mark)`.
- `a >> b` теперь значит каждый выход в каждый вход, а не `next` в единственный вход.
- `AsyncExecutor` переименован в `Executor`; `SyncExecutor` удалён. `run()` теперь возвращает асинхронный генератор, а не список: итерируйте его внутри корутины, например `asyncio.run(main())`, где `main` делает `[x async for x in ex.run(start, seed)]` — голый `asyncio.run(ex.run(...))` не работает. `fiber_workers` (теперь называется `threads`) / `gateway` / `max_inflight` переехали с исполнителя на `FiberExecutionController`.
- `ExecutorHandle`, `task.stop()`, `task.snapshot()`, `task.memory` удалены: тело не может остановить прогон или прочитать состояние исполнителя.
- `Task.links` удалён: тело не читает топологию.
- Модуль `actflow.fiber` удалён; импортируйте всё из корня пакета `actflow`.
- Контроллеры, переданные в `Task.__init__`, теперь прототипы: два узла, построенные из одной задачи, больше не делят состояние контроллеров.
- Свой контроллер исполнения теперь реализует `drive(stream)`, а не переопределяет `run`; `run` — готовый нормализатор на интерфейсе.
- `LinkRef` переименован в `NodePort`; `node["name"]` возвращает его.
- `ExecutionRuntime` удалён: пулом владеет `FiberExecutionController`; передайте `pool=`, чтобы делить его.
